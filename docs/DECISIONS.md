# 決定事項
実装していて問題を踏み、その結果として決まったもの。知らずに触ると同じ問題を踏むので、新しいコードでも同じようにする。

設計全体の方針は [DESIGN.md](DESIGN.md)、モデルの種類と測った値は [MODELS.md](MODELS.md) を参照。

## 推論

### Spleeter の fp16 版は WebGPU で動かさない
ONNX Runtime Web 1.30 の WebGPU で fp16 版を動かすと、エラーは出ずに出力がすべて 0 になった。入力は正しく渡っていた。int8 版・fp32 版は WebGPU でも正しく抽出できたので、fp16 版のときだけ WASM で動かす (2026-10-01)。

### WASM のスレッド数は 1 にする
マルチスレッドには COOP/COEP ヘッダーが要り、GitHub Pages などの静的ホスティングでは設定できない。どこでも動くことを優先し、`numThreads` は 1 に固定している。

### ONNX Runtime のメモリの上限は 1GB にする
WebKit は共有メモリの上限の分を、作った時点でプロセス全体の予約の枠（iOS で約 6GB）から差し引く。ONNX Runtime は上限 4GB で作るので、iOS では枠がすぐに尽きる。ビルド時に、Worker が渡す上限を使うよう書き換え（`ortMemory.ts`。書き換える場所が見つからなければビルドを止める）、既定は 1GB にする。設定の「開発者向け」→「抽出のメモリの上限」で変えられる（変えると Worker を作り直す） (2026-10-03)。

### 推論の Worker は止めずに使い続ける
ONNX Runtime はスレッドを 1 にしても、上限 4GB の共有メモリ（wasm）を作る。iOS Safari はこれを同時に 2 個までしか持てず、Worker を止めてもその枠はすぐには返らない。そのため実行環境を作り直すと `RangeError: Out of memory`（no available backend found）になった。iPad の PWA で、モデルや計算の種類によらず、2 回目から失敗した。
推論の Worker はページで 1 つだけ作り（`src/index.ts` の `sharedWorker`）、`dispose` ではセッションだけを手放す。中断は Worker を止めずに `cancel` で頼み、次のブロックで止める。準備に失敗した Worker は捨てる（ONNX Runtime は一度 wasm の準備に失敗すると、同じ Worker では二度と準備できない）。調べ方は設定の「開発者向け」→「抽出の診断」（`src/diagnose.ts`） (2026-10-03)。

### 曲は 512 フレーム（約 12 秒）ずつ処理する
1曲分のスペクトルを一度に持つと、スマホではタブが落ちる。ブロックごとに STFT → 推論 → マスク → 逆STFT を行い、進捗もブロックごとに知らせる。
ブロックは重ねずに区切る（sherpa-onnx の実装と同じ）。継ぎ目が気になったら、重ねてクロスフェードする方式を試す。

### 前後に N_FFT ずつ無音を足してから処理する
STFT は center なしなので、そのままだと両端のフレームだけ窓の重なりが揃わず、音が小さくなる。前後に 4096 サンプルの無音を足して処理し、最後に切り取る。

### ボーカルと伴奏の両方が要るときは、推論を1回で済ませる
ボーカル用・伴奏用のモデルはどちらも、マスクを作るのに両方の出力を使う。`separate` を2回呼ぶと推論も2回になるので、両方が要るときは `separateBoth` を使い、逆STFT だけを音ごとに行う。

### 約 11kHz より上は、既定では消す
モデルは 1024 ビン（約 11kHz）までしか扱わない。sherpa-onnx と同じくマスクを 0 にする（`'zeros'`）のを既定にし、1024 ビン目のマスクで延ばす方法（`'edge'`）も選べるようにしている。延ばすと伴奏の高い音が混ざりやすい。どちらが良いかは未定。

## 受け渡し

### ライブラリは React にも画面にも依存しない
受け渡しはチャンネルごとの `Float32Array` とサンプルレートだけにする。Web ツール（`app/`）からも、WeVocalSynth の追加機能からも同じように使えるようにするため。画面は `app/` に置き、`src/` からは `app/` を参照しない (2026-10-01)。

### 結果は入力と同じサンプルレート・チャンネル数・長さで返す
モデルは 44.1kHz・ステレオなので、変換して推論し、元に戻して返す。戻すときにサンプルレートの変換で 1 サンプル程度ずれることがあるため、入力と同じ長さにそろえる。使う側は長さが変わらない前提で置き換えられる。

### Worker に渡す配列は、呼び出し元のものなら複製してから移す
変換が要らなかった場合、入力は呼び出し元の配列そのもの。そのまま Worker に移す（transfer）と、呼び出し元の配列が使えなくなる。

### 中断は `dispose` で Worker ごと止める
推論の途中で止める方法が ONNX Runtime に無いため。処理中の `separate` は AbortError で失敗させ、待ち続けないようにする。

## Web ツール

### モデルは抽出のたびに読み込み、終わったら解放する
推論中は数百 MB 使う。スマホでメモリを持ち続けないよう、抽出ごとに Worker を作り、終わったら `dispose` する。

### 取得したモデルは Cache Storage に保存する
モデルは 38〜75MB あり、毎回ダウンロードすると遅い。初回に取得したものを保存し、2回目からはそれを使う。保存できなくても（容量不足など）、その回はそのまま使う。

### モデルはリポジトリに含めず、ビルドのときに配布元から取る
大きいため。`scripts/fetch-models.mjs` が sherpa-onnx の配布物を取得してサイトと一緒に配る。CI では取得した配布物をキャッシュする。

### PevenMUI は、隣にあればそちらを使う
WeVocalSynth の submodule として開発するときは、ルートの `pevenmui/` と `extractor/pevenmui/` が両方見え、違う方を直してしまいやすい。隣の `../pevenmui` を優先して使い、こちらは `git sparse-checkout` で隠す（`todo setup:nested`）。
外にある PevenMUI から読み込む React・MUI がアプリのものと2つにならないよう、`vite.config.ts` で `dedupe` している (2026-10-01)。
